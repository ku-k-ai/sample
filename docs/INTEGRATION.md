# 接続仕様

## 維持する処理

```text
既存の候補抽出・STEP1
  └ 請求項構造／担当範囲整合／不足事実／確認条件
       ↓ 本文確認が必要な候補だけ
STEP2_PLAN：正式ルールとの照合・必要条件の訂正・質問化
  └ 採用する範囲条件／質問と条件の対応／訂正履歴
       ↓ 検証→確認ID付与→計画保存
STEP2_REVIEW：全文の事実取得→工程対応→部分条件の確認→候補状態の更新
       ↓ 引用・状態を検証
既存STEP1で確定済みの候補と、STEP2で更新した候補を結合
       ↓ 確認計画・工程文脈・引用・状態を保持
FINAL_DECISION：選択可能な候補から主担当を比較
```

LLM呼出しを統合しない。STEP1で確定した候補を、理由なく再調査へ回さない。
STEP1の請求項構造と対応箇所は本文を読んでも書き換えない。

## 実装の差し替え箇所

1. STEP1の不足条件作成部分を差し替え、出力schemaへ `確認条件` を追加する。既存の候補表・工程推定欄を残す。
2. STEP2_PLANへ本文確認対象、正式なラベル・定義・代表例・振分け、STEP1結果を渡す。請求項に前段限定の命令文を混ぜない。
3. PLANの出力schemaに `採用する範囲条件`、`差戻事項` と、質問ごとの `確認観点`、`対象`、`条件根拠` を追加する。条件を訂正した記録は捨てない。
4. `freeze_plan` で質問を検証してIDを付ける。IDをモデルへ計算させない。計画と署名を保存し、REVIEW再実行時は同じ保存済み計画を使う。
5. REVIEWへ固定計画と原文全文を渡す。出力schemaへ `工程文脈`、各回答の `条件判定`・`代替成立ID`、候補ごとの `差戻事項` を追加する。
6. `validate_review` / `build_final_input` で検証・結合する。事実・引用・計画を落とす既存の要約処理は、この受け渡しでは使わない。
7. FINALの出力schemaへ `前段不整合` を追加する。従来の `搭載先ユニットの特定`・`候補評価`・`最終判定` 等は維持する。`validate_final` で選択資格と主担当件数を検証する。

これはプロンプトだけのコピーでは完了しない。追加項目を旧JSON schemaで拒否したり、ログ生成時に捨てたりしないようにする。未知の既存本体コードへ自動接続したとは扱わない。

## 質問の揺れをどう扱うか

質問文は4つの定型文に限定する。「どの正式ルールの、何の不足を確認するか」は別欄に残す。
STEP2_PLANの `採用する範囲条件` は候補全体の条件、質問の `判定する条件` は個々の部分条件である。複数の回答を合わせて全体条件を満たしてよい。
正式ルールの又は/かつ/除外の意味を、質問数や確認済み件数に置き換えない。
訂正前のSTEP1を履歴として残し、本文確認と最終比較では採用済み計画を使う。

計画を固定しても、STEP1による条件・対象・確認観点の選択まで決定的になるわけではない。
同じ入力でSTEP1を繰り返したときにそこが変わるかを別途計測する。ルールの解釈自体が毎回変わるものは、当該ラベルの正式条件を版管理して固定する対象であり、特許ごとに例外を増やさない。

## 事実、条件判定、候補資格を分ける

| 層 | 保持するもの |
| --- | --- |
| 取得事実 | 本文に何が書かれていたかと引用。条件を満たさなくても消さない。 |
| 部分条件 | 当該質問の条件が成立、不成立、未解決、又は代替条件成立により確認不要か。 |
| 候補資格 | 正式ルールの条件全体と除外条件を適用した結果。 |
| 主担当 | 資格のある候補の間で、どこの図面・制御仕様が変わるかを比較した結果。 |

「本文に存在する」と「正式担当対象の設計・機能と関係する」は別。
「画像形成のどの工程の働きに対応するか」と「実際の接続先」も別。
工程対応は原文事実を根拠にした技術的解釈として引き継ぐ。架空の接続の根拠には使わない。

## 候補状態

| 状態 | 選択資格と引き継ぎ |
| --- | --- |
| 整合確認済み | 選択可能。主担当の優先順位までは付けない。 |
| 本文確認が必要 | 選択不可。部分事実・引用・残る穴を最終段へ渡す。根拠付きで有力な未解決候補が結論を左右するなら最終は自信無。 |
| 明確に不整合 | 選択不可。正式な除外又は必要条件を否定する明示事実・引用を残す。 |
| 判定対象外 | 選択不可。全文を確認しても具体的な関係が得られなかったという処理結果。非該当の証明とは言わない。部分事実は残す。 |

未確認件数が多いから対象外にする、引用が1つでもあるから整合にする、という集約は禁止。
「未確認を落とすな」ではない。必要条件を正しく調べた結果で候補を絞る。
`確認不要` には同一候補内で成立した代替条件の確認IDが必要。補助質問や重複質問はPLANで除く。
差戻しは対象候補の条件訂正箇所と理由を記録する。自動無限リトライや最後のモデルによる資格上書きを行わない。

旧実装の `一部確認済み` は、この修正版のREVIEWの出力値にはない。単に未知語を整合へ変換しない。
必要条件が一成立経路についてすべて満たされ、残りが不要なら整合確認済み。必要条件が残るなら本文確認が必要に分けて接続する。

## 補助コードの呼び出し

標準ライブラリのみ。入力はJSONデコード済みの辞書・配列。
`all_candidates` は旧STEP2を含まないSTEP1時点のスナップショットとする。
各候補のキーは `候補ID`、`ラベル`、`正式担当範囲`、`STEP1`。

```python
from patent_pipeline.guards import freeze_plan, build_final_input, validate_final

pending = [c for c in all_candidates
           if c["STEP1"]["担当範囲整合"] == "本文確認が必要"]

# plan_output: STEP2_PLANのJSON出力
locked = freeze_plan(plan_output, pending)
# lockedを保存。REVIEWにはlocked["計画"]を渡す。
# sources: モデルに渡した原文と同一の {抜粋ID: 原文}。
# full_textはモデル出力からではなく、原文取得・入力組立側で設定する。
handoff = build_final_input(
    all_candidates, locked, review_output, sources, full_text=True,
)
# FINALにはhandoff["工程文脈"]、handoff["候補"]、
# handoff["選択可能候補ID"]と既存の請求項・構造整理を渡す。
validate_final(final_output, handoff)
# 検証通過後のみ、最終候補IDを入力の正式ラベルへ対応付ける。
```

上は既存の呼出し処理へ組み込む断片であり、それだけでLLMを呼び出すスクリプトではない。
本文確認対象が0件なら既存のSTEP2スキップを維持する。この補助コードを無理に呼ばず、STEP1の根拠・工程解釈と選択資格を引き継ぐ。

## 機械検証で防ぐこと／防げないこと

防ぐ：定型外の質問、固定後の計画変更、IDの追加・欠落・重複、存在しないルール引用・本文引用、未確認の成立への格上げ、部分本文での確認完了、候補の無断復活、主担当の複数選択。

意味判断は別途必要：ルール原文から導いた条件が正しいか、OR/ANDを意味的に保存したか、引用が条件を本当に支持するか、工程対応が妥当か、全文を意味的に網羅して読めたか。原文一致の検査だけでは保証しない。
機械検証失敗は `ContractError` として止める。失敗を自動的に「自信無の正常結果」へ置き換えない。

## 実行履歴と移行

新旧の結果を混ぜない。今回の再実行では、旧STEP2結果と選択可能IDを再利用しない。
元の請求項、本文、ルール、候補IDは同じものを使い、入力組立の命令文混入を解消する。
キャッシュキーは原文、ルール、プロンプト、モデル設定、schema版、固定計画署名を含める。
古いキャッシュやログは削除せず別run_idで残す。署名は改変検出用であり、正しさの証明やモデル出力の認証ではない。
